# 意图识别第三轮优化与评测

本轮修复了已经确认的两类误写入口，并修正了相邻否定的范围；**没有证明整体意图正确率或新题泛化有所提升**。真实 LLM 运行仍受超时、返回标签和置信度影响，所有失败样本均保留。

## 已落地的改动

- **把被查找的动作名称保留为对象。** “找出订单编号的生成函数”现在保留 SEARCH/READ，不再额外创建函数；“查看删除文件的代码”不会产生 DELETE。读取或审查结束后真正的创建、修改命令仍保留，包括“审查完代码立刻生成函数”。
- **阻止背景文案成为 LLM 写入依据。** 对支持的“按钮文案是‘执行数据库迁移’”等内容归属句，规则和语义入口使用同一屏蔽范围；引用之后的口语请求仍按原始偏移送入模型。独立的明确释义请求只允许 READ/ANALYZE/COMPARE 提议，错误或高置信度的 CREATE/UPDATE 不会越过这一边界。
- **保留肯定请求和后续否定的各自范围。** “审一下改动，这次不用重构，也不用跑测试”保留 REVIEW，同时保留两个禁止动作。
- **区分已不使用的状态和禁止操作。** “旧文件已经不用了，直接删除这个文件”保留明确删除及文件目标；“不用删除”“删除的要求已经取消”等真正否定继续有效。

生产变化是修改 `minicode/intent_parser.py`、`minicode/intent_negation.py`，新增 `minicode/intent_request_roles.py`。另更新说明并新增三组测试。没有修改模型配置、提示词、校准、阈值、全局用户开关或已有题目标注。

这些是有界语法修复。归属句采用有限的来源名词结构，无法确认的写法仍走原有逻辑；不能据此声称已识别所有背景、假设和讨论请求。

## 完整解析结果

“完整解析”要求该题预先标注的主意图、动作、肯定/否定、只读、实体和顺序等检查全部通过。以下四个题集分别报告，不能合成一个新题泛化成功率。前三组共 130 题已用于开发；T01–T50 是本轮冻结代码后首次解盲的新题。

| 题集 | 禁用 LLM，前→后 | 真实 LLM，前→后 | 本轮后真实 LLM 主意图正确 |
| --- | --- | --- | --- |
| 原 50 题，C01–C50 | 34→34/50 | 43→43/50（86%） | 43/50 |
| 第一批 40 题，N01–N40 | 22→22/40 | 29→29/40（72.5%） | 35/40 |
| 上一轮 40 题，H01–H40 | 11→14/40 | 29→28/40（72.5%→70%） | 29/40 |
| 本轮新 50 题，T01–T50 | 21→21/50 | 36→33/50（72%→66%） | 34/50 |

四组禁用模式均无完整通过回退。H13、H33、H36 在禁用和真实 LLM 两种模式都由失败变为通过，分别对应状态否定、名词宾语、相邻否定修复，是可归因于代码的完整解析收益。

真实 LLM 下，H03 从接纳变为低置信度，H07/H24/H26 从接纳变为超时，抵消了上述三题收益。原 50 题中 C09 从超时恢复，C23 从通过变为超时；因此总分不变。对这六个发生转变的开发题，用三个固定适配器分别跨版本离线重放，共 18 对请求与结果一致，未发现新规则误拦导致这些转变。

| --- | ---: | --- | --- |
| C01–C50 | 22 | C40 | 无 |
| N01–N40 | 19 | 无 | 无 |
| H01–H40 | 23 | H33 | 无 |
| T01–T50 | 30 | T05、T11 | T05、T11 |

C40 的已知错误模型 UPDATE 提议在旧快照中会被接纳，在新代码中对应背景不再触发模型调用。该题仍按 QUESTION/READ 解析，而冻结标签要求 EXPLAIN，因此**不能说 C40 已完整答对**；本轮修复的是误写边界。

H33 的“生成函数”不再被当成 CREATE，该题完整通过。新题 T05“应该怎样重构？只讨论方案”仍被规则解析为 REFACTOR/UPDATE；T11“那个命令会改动工作区里的文件吗”仍出现 CODE/UPDATE。两版都有这两项确定性误写，表明泛化的讨论/疑问角色仍没有处理完整。

## 新 50 题下降的原因

新题的代码侧结果没有可测的改善。独立复核使用三种固定适配器：空提议、修复前真实运行已接纳的提议、修复后真实运行已接纳的提议。每种适配器运行完整 50 题，比较两版的 `SemanticIntentRequest`（文本、上下文、确定性操作）及去除时间戳的完整最终解析，**150 对全部一致**，触发同样的 21 个题目。此验证没有重新调用模型，也没有重建未保存的原始模型响应。

真实运行中的变化为：

- T01/T08/T17/T21/T38 从通过变成超时；T23 从正确解释标签变成 CHAT。
- T19/T42 从超时恢复；T44 从 provider error 恢复。
- 其余题目完整通过状态不变。最终 33/50，不能把这些前后变化归因为本轮代码提升或退化。

候选新题运行有 5 次超时，修复前有 2 次超时和 1 次 provider error；两版均有一个 invalid response。模型、5 秒超时、输出上限和校准设置相同。每个版本每题只运行一次，不能给出稳定提升或显著性结论。

调度中，新题修复前运行的末尾与候选运行的开头重叠约 **2.630 秒**（候选 freeze 至基线 summary 的文件时间差）。保留原始两次样本，没有为获得更高分重跑；该短暂重叠不能解释所有超时，也不将两次耗时差视为性能实验。

## 剩余问题及优先顺序

1. **把讨论、疑问、假设作为完整请求角色处理。** T05/T11 说明，即使明确出现“怎样”“吗”“只讨论”，动词规则仍可能生成修改操作。这需要更完整的句子角色与动作证据约束；仅在低置信度时调用 LLM 无法纠正已经高置信度匹配的错误规则。
2. **改善只读请求的召回和否定范围。** T07/T09/T16 等保持 UNKNOWN 且跳过兜底；否定运行测试不应吞掉解释参数或补充测试的独立任务。需要按语段保存有效肯定请求和各自的限制。
3. **统一任务类别与动作。** T22 的解释被标为 DEBUG，T25 创建函数被标为 DOCUMENT，T39 普通构建命令被标为 TEST，T47 新增 dry-run 功能也被标为 TEST。当前关键词优先级仍会压过实际请求类别；部分复合步骤也缺失。
4. **单独评估调用稳定性。** 本次超时集中影响依赖语义兜底的题目。应预先固定重复次数，分别比较超时、延迟和语义准确率；若调整超时或模型，要作为单独实验，不与规则修复混算。本轮没有放宽超时或重试限制。

T01–T50 已解盲，后续可以加入开发回归集；若要评价下轮泛化，必须另建未见题。此前的系统操作、部分配置/否定类别、历史方案指代和文档行目标等缺口也仍存在，未在本轮扩张处理。
