# 意图识别第一轮优化与复测

已完成规则边界修复、LLM 调用控制和诊断补充。原 50 题开启 LLM 后，完整通过率从 **31/50（62%）提升到 40/50（80%）**；独立新 40 题从 **21/40（52.5%）提升到 24/40（60%）**。新题收益较小，说明这轮对已定位问题和模型响应可靠性有效，广泛自然语言的解析仍有缺口。

## 测量结果

“完整通过”要求该题预先标注的主意图、动作、肯定/否定、实体、只读属性和顺序检查全部通过；不是只判断一个分类标签。各行优化前后采用相同题库和相同计分契约。

| 题库与模式 | 优化前完整通过 | 优化后完整通过 | 主意图正确数变化 |
| --- | --- | --- | --- |
| 原 50 题，规则模式 | 23/50（46%） | 31/50（62%） | 26 → 34 |
| 原 50 题，LLM 开启 | 31/50（62%） | 40/50（80%） | 33 → 42 |
| 新 40 题，规则模式 | 16/40（40%） | 18/40（45%） | 24 → 27 |
| 新 40 题，LLM 开启 | 21/40（52.5%） | 24/40（60%） | 27 → 32 |

原 50 题有 10 题从失败变通过，1 题 C02 因本次 5 秒超时从通过退回未知，净增 9 题。新 40 题的 LLM 对照净增 3 题，没有通过变失败。原 50 题已用于定位和开发；新 40 题的候选规则与候选 LLM 各运行一次，之后未根据其结果修改生产代码。

## 修改内容

1. **区分动作和讨论对象。** 配置文件、异常处理逻辑、误删描述、假设事件、引用内容不再仅因出现动作词就生成操作。撤回和局部否定的作用范围更准确，后续真实命令仍保留。
2. **处理文档与记忆边界。** “补充部署步骤”继承明确的文档目标；新增代码功能仍进入代码操作。“记住”需要处于命令位置，查询历史偏好或讨论“记住密码功能”不会直接变成记忆写入。
3. **防止兜底重新引入已排除的片段。** 纯引用、报告前缀和假设片段不再作为未覆盖的指令发给 LLM；事故描述后的真实恢复请求仍保留入口。
4. **改进真实模型调用。** 语义分类默认超时从 1.5 秒改为 5 秒，输出预算从 256 改为 512 token；经提供方能力验证后启用 JSON object 输出和 `low` 推理强度。目前这两项提供方参数仅开放给官方 BigModel 路由上的精确 `glm-5.3-flash` 模型，其他路由不附加这些参数。
5. **补充可观测性。** 记录有限的结束原因、输出字符数、输出是否触顶和所用控制参数。长度截断即使留下可解析 JSON 也不接受；原有本地校验、调用预算、取消和零重试约束继续生效。

只改动了本轮负责的 7 个生产 Python 文件；其余 249 个已有 Python 文件与修改前快照一致。配置示例、文档和对应测试已更新。评估时在内存中启用 LLM，未修改用户私有配置；功能仍默认选择性开启，已有显式配置优先于新默认值。

## LLM 调用效果

对照使用实际配置的 GLM 模型。优化前使用此前验证过的 10 秒超时和 256 token；优化后使用新的 5 秒、512 token、JSON object、低推理默认参数。没有执行题目中描述的文件、命令或系统操作。

| 指标 | 原 50 题：前 → 后 | 新 40 题：前 → 后 |
| --- | --- | --- |
| 调用尝试数 | 18 → 16 | 16 → 15 |
| 获得提供方使用量的完成响应 | 17 → 15 | 16 → 15 |
| `invalid_response` | 7 → 0 | 9 → 0 |
| 超时 | 1 → 1 | 0 → 0 |
| 被触发调用的中位耗时 | 5.59 → 1.53 秒 | 5.96 → 1.99 秒 |
| 完成响应的提供方输出 token 总数 | 3306 → 499 | 3475 → 605 |

这些耗时来自各次实际触发的调用集合，集合会随规则覆盖变化，并非严格逐调用的单因素延迟实验。JSON 可解析也不等于意图正确：优化后原题还有 4 次低置信度和 1 次主动弃权，新题还有 4 次低置信度和 2 次主动弃权。完成事件和失败事件均保留在原隔离运行日志；未获得此模型的可靠金额定价，因此没有推算费用。

## 仍然存在的问题

- **只读边界尚未全面解决。** 原题 22 个标注为只读的请求中，明确误生写入/删除操作的 5 例降至 0；新题 19 个只读请求中，仍有 2 例，优化前后相同。N10 的“解释它想解决什么问题”产生 `debug/update`；N21 的“运行脚本时出现问题”被当成当前 `test/execute`。未知意图导致的 `is_read_only=False` 单独统计，没有混算成写操作。
- **主意图和动作标签仍有混淆。** 问题解释、问题诊断、代码修改、重构、配置和系统操作之间还会选错或漏掉标签。原题 C30、新题 N18 等系统操作没有被正确识别。
- **上下文与实体不完整。** “后一个文件”“第二个先不做”等指代，以及 `.coveragerc`、日志文件、被引用文件的实体提取仍有遗漏；复合任务也可能漏掉一段。

下一轮优先做统一的“当前请求 / 背景描述 / 禁止动作”表示和语义结果复核，避免每种表达各加一条补丁；随后补主意图选择、复合操作覆盖和上下文实体绑定。继续使用新的独立题库验收，而不是反复针对这 40 题提高分数。

## 验证与证据

- 意图与 Skill 路由相关回归 **2381 项通过**；适配器和配置专项 **205 项通过**，两者有部分重叠，不相加宣称总数。
- 新解析测试 66 项、提供方测试 37 项、分类交付测试 11 项全部通过。相同最终测试字节在真实修改前源码快照上分别出现 45、36、9 项失败，其余为本来就通过的控制用例。保存了具体反例证明。
- 相关 Ruff 检查、编译检查通过。独立审查发现的 5 类新增回归均已修复，固定 16 例复核通过。
- 修改前快照重新运行原 50 题，得分及详细意图记录与原报告一致，仅时间戳不同。正式运行的源码、题库、计分器和脚本冻结校验通过；汇总遇到失效校验会拒绝生成正式比较。

新 40 题的作者在候选首次运行前、未查看任何实际结果时发现：旧计分器会把备选标签的动作当成全部必需。原题库和标签字节保持不变；16 题的作者备选动作分组另行冻结，24 题完全沿用原检查。并列任务、显式必需/禁止项、实体、只读和顺序要求没有放宽。已保存的基线结果用同一冻结契约离线重计分，原始分数也保留；没有重新调用模型挑选结果。两套题库的完整率分别比较，不合并成一个“90 题准确率”。330 项人工构造检查验证了这份计分契约。

实体检查针对当前解析结果的顶层实体，不保证每个操作都绑定了正确目标。例如新题 N31 完整通过，但文件只出现在顶层上下文实体中；这仍不是下游工具执行正确的证明。

这是小规模合成题的单次对照，不能直接视为线上准确率或操作安全保证。
