# 意图识别：根因与优化路线

2026-09-07。本次只复核已有证据与代码、核对官方模型文档，没有新增模型调用或修改生产行为。

## 判断

当前主要限制来自规则结果的纠错机制、语义调用的输出预算，以及结构化任务信息不足。现状是规则先认定操作，LLM 仅补充尚未识别的内容，后续保留原操作并按动作优先级选主类型。这使错误规则匹配很难被后续纠正。

10 秒轮严格通过 31/50。剩余 19 条按实际处理路径拆分如下，三组互斥：

| 处理路径 | 题数 | ID |
| --- | ---: | --- |
| 跳过语义兜底，仍不满足标注 | 12 | C15、C17、C21、C32、C34、C35、C38、C39、C46、C47、C48、C50 |
| 模型返回无效，最后仍不满足标注 | 5 | C11、C23、C25、C30、C40 |
| 模型提案被接受，但不满足冻结标签 | 2 | C26、C33 |

这是一张处理路径表，不表示组内所有问题有相同根因。例如 C30 的 system 类型本身不在当前语义提案允许集合中，解决无效响应后也不能直接得到期望标签。

C26 的 review/compare、C40 的 question/read、C47 的 code/update 是可以接受的较粗分类。把这三条解释为近义结果后，仍有 16 条实质或结构问题，因此评测口径只能解释一小部分低分。原始标签保持不变。

## 已证实的根因

### 1. 规则命中被当成已解决，缺少复核

[目标选择](../../../minicode/intent_parser.py#L8302)只允许整句无操作，或恰好一个未覆盖且非否定的分句进入语义推断。[合并过程](../../../minicode/intent_parser.py#L8357)将语义提案追加到规则操作中，不撤销原结果。

因此 C15 查文件位置却匹配 configure/update，C17 审查异常处理却匹配 debug/update，C32 已取消的修复仍是肯定 update，均不会自动被 LLM 修正。开关和模型能力对未送入模型的部分没有帮助。

[规则置信度](../../../minicode/intent_parser.py#L9135)由固定公式给出，不是样本校准后的正确概率。C15 的错误仍可达到 0.92。不能单凭这样的高分决定跳过复核；本次没有 low_confidence 失败，降低接受阈值也不针对主要问题。

### 2. 对话中的动作角色混在一起

“执行删除”“解释删除”“假设已删除”“指出误删风险”“撤回删除”都包含动作词，但对应不同任务。C35 的“误删文件”被切出 code/delete，C38 假设删除成为肯定删除，C34 的禁止跨句污染后续解释。

[主操作选择](../../../minicode/intent_parser.py#L9145)又按动作优先级排序：删除高于更新，更新高于审查/解释。错误抽出的删除会压过正确的审查；C33 中补出的阅读步骤也能在同级时抢占后面的分析目标。应将“用户当前主要目标”和“操作风险等级”分别表示。

### 3. LLM 传输与输出配置尚未适配任务

默认 1.5 秒轮 18 次全超时；10 秒轮调用中位数约 5.59 秒。10 秒轮七次无效响应全部达到 256 输出 tokens，其中六次没有正文。这是输出预算或响应形式不匹配的明确排查线索，尚不能确定具体推理消耗、截断或格式原因。

现分类调用只传禁工具、256-token 上限、温度等参数，没有显式传 reasoning_effort，也没有请求提供方 JSON 模式。GLM-5.3-Flash 的官方模型卡说明 reasoning_effort 支持 low/high/max，未指定时默认为 max。应验证当前 API 端点的对应行为，优先对比低推理强度，而不是直接假定通用关闭思考参数适用于该模型。[官方模型卡](https://huggingface.co/zai-org/GLM-5.3-Flash)

智谱官方文档给出的结构化路径是 response_format.type=json_object，再对返回值做本地 schema 验证。它与当前 adapter 的 OpenAI 原生 json_schema 开关是不同能力，应该按提供方明确适配。[官方结构化输出文档](https://docs.bigmodel.cn/cn/guide/capabilities/struct-output)

### 4. 返回协议不能完整表达任务

现 LLM 提案仅有 intent/action/confidence，不能直接补目标实体、引用绑定、禁止/撤回或 system 类型。已有 operations 与 typed test constraints 是可复用的基础，但作用范围和上下文连接仍不足。

C46“后一个文件”、C48“再加一个用例”有动作却丢目标。C50 的“其他内容不动”使尚未识别的整句被视为有否定，从而跳过 LLM，实际需要的是“只更新已指明的那一行”这种局部范围约束。

## 建议的实施顺序

### 第一阶段：修正动作误判，同时让语义调用稳定返回

这两条工作线可以并行，但上线前应优先验收误修改、误删除问题。

**动作处理线：**先把当前指令、引用、假设、风险描述、历史任务、撤回区分为带原文位置的候选证据，再决定哪些候选是当前肯定操作。对“只审查”“先取消”“假设”与修改动作同时出现的请求进入复核。复核可建议保留、改类、丢弃或补充操作，最终必须由本地规则验证原文、上下文与适用范围。模型解释不直接形成执行权限；解除已有明确限制必须有当前用户原文证据。

**语义调用线：**为提供方增加受控的 JSON 模式与推理强度参数，先做 low 推理强度、512/1024 tokens 的分步对照，保持阈值和题库不变。补记 finish_reason、正文长度、用量来源和可用的推理 token 数，不记录隐含推理全文。先确认为什么无效，再决定是否需要有界重试；超时预算依据实际延迟分布选择，10 秒仅是已测诊断条件。

验收关注：现有危险误判用例及独立同义/否定变体没有额外写操作；有效结构化返回率提高；所有请求仍满足取消、超时、总调用数和 token 预算约束。

### 第二阶段：把“补漏”扩展为有证据的纠错

保留明确命令的快速规则路径。让模型复核低覆盖、证据冲突、撤回/假设复杂、目标缺失，以及读取请求出现写候选的情况。不要仅以 UNKNOWN 或规则固定置信度作为触发条件。

复核输入包含完整当前请求、受限历史、候选操作与原文证据。输出使用候选 ID、实体候选 ID 和经过校验的位置绑定；原文由本地保留。这样模型可以指出某个 code/delete 来自假设，或某个 update 已被撤回，同时避免由模型自由生成路径或权限。

规则与模型的意见进入同一套约束检查：当前用户任务、禁止的作用范围、后来明确撤回/释放的顺序、原文位置、参数目标都须一致。对不明确的写目标保留未解决状态；明确的只读部分仍可继续处理。

验收关注：C15/C17/C21/C32/C34/C35/C38 等被纠正；引入复核后，原本正确的近义问法与动作范围不被破坏。需要单列 false-write 和 false-veto 指标，避免通过拒绝所有请求取得虚假的安全成绩。

### 第三阶段：补齐上下文、目标与主任务

在现有 IntentContext/operations 基础上增加必要的结构信息：当前目标、有顺序的焦点实体、未完成步骤、约束范围与生效轮次。这样“后一个文件”有可验证的候选顺序，“再加一个用例”能继承被测函数，而话题切换能清除旧目标。

操作表达覆盖“做什么、对什么、是否执行、在哪个范围、先后关系、证据来源”。将主要目标与实现步骤分开，例如阅读代码是分析原因的手段；删除候选的风险等级不应决定用户主要想做什么。

system 请求走可审计的命令映射或受限命令候选，再按真实执行权限处理。语义分类成功不直接执行系统操作。

验收关注：C46/C48/C50 及新多轮变体能恢复正确目标；不继承过时任务或被取消的动作；同时测试目标错误、目标缺失、多步顺序和多余操作。

### 第四阶段：用新数据决定架构与成本

现有 50 题转为回归集，另做约 200–300 条新的中文自然表达、英文、中英混合、引用、撤回和多轮样本，优先纳入经允许使用并脱敏的真实请求。按语义家族划分开发与保留集，避免同一句的改写跨集合泄漏。

在相同题库上比较四种候选：规则、规则加当前补漏、规则加有证据的复核、全量语义解释加本地约束检查。这样才能判断模型本身、触发策略与后处理各自的限制。全量模型方案先作为对照，不预设它一定最优。

分别看主要目标、操作集合、目标绑定、禁止/撤回、错误写操作、错误拒绝、unknown/澄清、结构化返回率、P95 延迟与成本；语义近义与真正动作错误分开标注。延迟测试记录顺序与缓存条件，模型配置至少做少量重复验证稳定性。

等质量与真实调用分布稳定后，再评估专用的小模型或分类器、缓存和压缩提示词。当前没有数据支持承诺一次优化即可达到某个总体准确率。

## 第一轮建议交付范围

优先完成“提供方结构化输出与低推理强度适配”以及“撤回/假设/只读请求的写动作纠错”，保留现有公共解析入口和预算观测约束。交付物应包括改动、完整旧集回归、新独立语言变体、paired 结果和每项失败归因。随后再处理上下文结构与主目标选择。
