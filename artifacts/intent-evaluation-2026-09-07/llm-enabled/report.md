# 开启 LLM 语义兜底后的 50 题对照

2026-09-07。**有提升，但仅开启默认配置没有改善；把超时从 1.5 秒延长至 10 秒后，全部已标注要求通过率由 46% 提升至 62%，增加 8 题、16 个百分点。**

## 结果

| 条件 | 主意图符合冻结预期 | 全部已标注要求通过 | 实际语义调用 |
| --- | --- | --- | --- |
| 原始：关闭兜底 | 26/50，52% | 23/50，46% | 0 |
| 仅开启，保留默认 1.5s | 26/50，52% | 23/50，46% | 18；全部超时 |
| 开启，超时改为 10s | **33/50，66%** | **31/50，62%** | 18；10 accepted、7 invalid_response、1 timeout |

两轮均有 32 题跳过语义推断。没有出现“原本通过、复测未通过”的题；这只描述冻结评分，不代表每个语义结果都没有变化。10s 轮 C33 新增 search/read 并改变主类型，该题前后均未满足冻结要求。

模型为当前配置的 **glm-5.3-flash**，使用 `open.bigmodel.cn` 的生产 OpenAI-compatible 适配器。默认实验只覆盖 `intentSemanticClassifier.enabled=true`；第二轮再覆盖 `timeoutSeconds=10`。其余关键参数均保持原值：阈值 0.72、输入上限 4000 字符、输出上限 256 tokens / 4096 内容字节、temperature=0、零重试，使用内置 bootstrap 校准。

**开启范围为本次评估进程；用户全局配置未持久修改。**这避免将对照实验的参数直接应用于其他正在运行的会话。生产源代码、模型提示词、题目、预期和原评分器均未修改。

## 仍然存在的问题

**之前的动作边界错误没有被修复。**22 条预期读取/分析的题中，仍有相同的 5 条输出了肯定的修改或删除操作：

- C15 查配置文件位置 → configure/update。
- C17 审查 PR 的异常处理 → debug/update。
- C32 已取消的修复 → 仍有 debug/update。
- C35 撤回测试、审查误删风险 → test/create 与 code/delete。
- C38 假设文件被删除 → code/delete。

C21 的文档部署说明仍被当作代码/配置更新；C34 的否定范围错误、C46/C48 的历史目标缺失以及 C50 的文档指代也未解决。这些题均跳过语义兜底。

原因在当前接线：兜底接手完全未识别请求，或复合请求里唯一未覆盖且非否定的分句，然后**追加**经过本地验证的操作；它不撤销已有规则操作。可见 [fallback 目标选择](../../../minicode/intent_parser.py#L8302)与[操作合并](../../../minicode/intent_parser.py#L8357)。因此，正确补充一些 unknown 并不能纠正规则已经错误认定的动作。

这里只测建议性的意图解析，没有运行题目中的任务，也没有验证下游 Skill 排序、权限决策或工具执行。

## 为什么默认开启无效

默认 1.5s 轮的 18 次请求全部超时。10s 轮触发模型的 18 条耗时中位数为 **5.59 秒**；相比之下，1.5s 轮约为 **1.51 秒后放弃**。本次网络、模型和输出设置组合下，默认时间预算不足。

10s 轮仍有 7 次 invalid_response。生产观测记录显示：

- 7 次均报告 `outputTokens=256`，正好达到输出上限。
- 其中 6 次 `contentPresent=false`；C37 有内容但未通过校验。
- 这提示 256-token 上限与当前模型返回形式需要进一步验证，但仅凭这些事件不能确定是具体的推理 token 消耗、截断还是格式问题。本轮没有保存原始模型 completion，也没有改输出上限再挑选最好成绩。

因此，延长超时解决了“等不到结果”的一部分问题，结构化返回的有效性仍有空间。

## 调用成本与耗时

两轮共发起 **36 次模型调用**：不是把每题都强制交给模型。每题最多一次，保持生产兜底触发逻辑。

| 指标 | 默认 1.5s | 10s |
| --- | --- | --- |
| 发起 / 收到完成响应 / 失败 | 18 / 0 / 18 | 18 / 17 / 1 |
| 触发模型的题：耗时中位数 | 1.51s | 5.59s |
| 50 题串行总墙钟时间 | 27.87s | 92.76s |
| 账本输入 / 输出 tokens | 12,561 / 0 | 10,617 / 3,306 |

默认轮输入 tokens 全为超时后的保守估算；输出为 0 表示未取得用量回执，不表示服务端一定没有生成。10s 轮 17 个完成响应报告 provider 输入 9,919、输出 3,306 tokens，另一次失败记入 698 输入估算。缓存 token 信息另见逐题事件，不在此重复加算。

**实际费用无法可靠汇总**：10s 轮 17 个 cost 事件均为 unavailable，默认轮没有完成后的费用事件。不可把账本的 0 成本或缺失费用视为免费。

新 runner 使用公开 `parse_intent`，语义适配器存在时每题构造 parser；旧基线复用 parser。所以不应把全体请求中位数差全部归因于 LLM。上述模型调用子集耗时和总墙钟时间更有解释力。

## 可复核性与边界

三组均为同一 50 条合成请求及历史上下文，使用原评分器。每轮开始前验证原始 8 个冻结文件的 SHA-256，保存本轮安全配置、runner 与 baseline 结果哈希；每题采用生产 AgentTurnBudget、取消令牌、父截止时间及真实 RunObservation，日志写入隔离 RunJournal。没有初始化 MCP，也没有可执行工具。

独立复核检查原始题目、评分、模型 started/终止配对、持久日志与内存观测一致性、预算 reservation 结算及冻结文件。accepted 仅说明模型返回通过 schema/校准，不等于满足用户任务；例如 C26、C33 在冻结口径仍失败。

10s 是观察到默认全部超时后追加的参数诊断，未重新选题或修改标签。每配置只运行一次；本轮不是新盲测或多次重复的统计估计，不能从这 50 题推断真实流量准确率。
