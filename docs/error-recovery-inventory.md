## 系统实际怎样恢复

错误恢复分散在模型适配器、Agent Loop、工具层、工作流、持久化和界面层，没有一个能统一处理所有错误的事务或重试引擎。须区分以下行为：

| 类型 | 含义 | 典型实现 |
|---|---|---|
| 自动再尝试 | 在明确条件和上限内重新请求 | 模型暂时性 HTTP 错误、标明 retryable 的工作流阶段 |
| 换方案或降级 | 以较弱的能力继续，原动作未必成功 | 搜索换 provider、摘要回退规则、Skill 排序回退确定性结果 |
| 状态恢复与补偿 | 核对已发生的事实、补齐未完成记账 | Session delta、Turn 已提交结果重放、Curator outbox 补投 |
| 隔离与有限回滚 | 限制故障影响或撤销部分本地变更 | 工作流独立副本、archive staging 合并回滚 |
| 明确停止与清理 | 报告未完成并释放资源 | 拒绝重复调用、预算截止、终止进程组、权限超时 |
| 定义存在但未兑现 | 有名字、策略表或库代码，没有实际闭环 | SelfHealing 的部分动作、空目标的自动备用模型路径 |

下面按四个子系统列出 120 条审计记录：A 主执行链 30 条、B 工具和界面 39 条、C 编排与进程 23 条、D 持久化和 Memory 28 条。记录包括恢复、降级、停止和缺口；同一机制在上下游可分别出现，**不能把这个数字说成 120 种独立自动修复能力**。

## 必须先说明的限制

1. 工具错误分类主要给模型恢复提示，不负责直接重试工具；并不存在通用工具事务、幂等重发或自动撤销机制。
2. 进程重启恢复已提交的结果和记账，不自动从失败的模型或工具步骤继续执行。聊天断线也不会自动重发原 POST。
3. 普通 write/edit/patch 最终直接写文件；batch copy/move/delete 没有事务回滚。archive 的有限回滚不覆盖断电和回滚自身失败。
4. 工作流没有“测试失败 → 自动修代码 → 再测试”的闭环；严格验证失败通常停止。父工作区发生冲突也不会自动 merge。
5. `ModelSwitcher` 显式切换有效模型是真实现，但错误路径传空目标，没有自动选择默认备用模型。
6. `SelfHealingEngine` 的降低并发、缩短超时、安全模式、强制终止动作仅返回成功字典；其成功率没有复验故障是否消失。真实 Feedback 调参和独立进程清理应分开评价。
7. Memory 完全坏 JSON 不会自动从 `.bak` 或 Markdown 恢复；已经激活的 Hybrid 检索失败会停止注入 Memory，不回退 BM25 放行。
8. `storage_health` 只诊断。某些辅助状态仍直接写文件；不能宣称全系统的保存都原子、可自动修复。

后文逐项给出触发条件、动作、上限、停止边界与源码；每个子系统末尾另列未接线、占位或保障不足的部分。

### 有定义但不应夸大为生产自动恢复

1. `SchedulerExecutionPolicy` 的 Executor/Verifier 两次上限只是一项能力；当前生产相应错误通常非 retryable，不能写“执行/测试失败会自动改代码再跑一次”。Reviewer 否决也没有自动回到 Executor 的修复闭环。
2. `adjudicator_max_attempts` 可 host 配成 2/3，但当前生产默认 1；带 `retryable=True` 的 malformed verdict 分支不是当前默认会重问。
3. `background_tasks.register_completion_callback`/`check_completed_tasks` 实现了最多触发一次和 callback exception 隔离（[background_tasks.py:325](</Users/zhourunbo/code/coding agent/MiniCode-Python-main/minicode/background_tasks.py:325>), `:347`, `:160`），本次 `rg` 未发现 `minicode/` 内除定义/exports 之外的生产调用点。不要称内置自动完成通知/watchdog；状态刷新和 dispose 收尾已有真实调用。
4. `cancel_background_task` 有 host API 且由 shutdown 调用，但当前未发现独立用户工具的直接 cancel 调用，不能写成已经对用户开放的 cancel 工具。
5. 工作区“事务”不提供 arbitrary crash rollback；apply 中断只做事实核对。没有全系统 durable scheduler 断点续跑、失败 worker 自动换实例、整机重启后 background task 自动接管的证据。
6. `ProgressController.STOP/REQUEST_CONFIRMATION` 在生产 agent loop 仅 `logger.warning`，之后照常 `continue` 下一轮模型（[agent_loop.py:4592](</Users/zhourunbo/code/coding agent/MiniCode-Python-main/minicode/agent_loop.py:4592>), `:4602`, `:4610`）。`CyberneticOrchestrator` 同样仅把 decision 写 summary 并 warning（[cybernetic_orchestrator.py:479](</Users/zhourunbo/code/coding agent/MiniCode-Python-main/minicode/cybernetic_orchestrator.py:479>)）。所以不是实际停机/要求用户确认的闭环控制，其他独立 budget/cancellation 边界才真正停止。
7. `pipeline_engine.StepExecutor.execute` 的递归 exception retry 是独立库能力（`:266`, `:280`）；`Step.max_retries` 默认 **1**（`:61`），计数先加再判断 `< max_retries`，因此默认实际执行一次、没有额外 retry。默认 read/generate/modify/execute/document/notify handler 多只是返回描述字典（`:300`–`:330`）。生产 agent loop 仅 `get_pipeline_engine()` 初始化（[agent_loop.py:2134](</Users/zhourunbo/code/coding agent/MiniCode-Python-main/minicode/agent_loop.py:2134>)），没有调 `.run/.execute`；唯一库内部接线为 `process_task → engine.run → execute → executor.execute`（[pipeline_engine.py:441](</Users/zhourunbo/code/coding agent/MiniCode-Python-main/minicode/pipeline_engine.py:441>), `:344`, `:365`），`minicode/` 未发现 `process_task` 的生产调用方。不能把它计入当前主 agent 的自动任务/命令重试。旧 `py-src/` 副本也不能证明根 `minicode/` 主链已接线。

### 给主报告的优先结论

- 真正自动重做：少数明确标注可重试的工作流阶段、有限 JSON 格式修复、模型步骤耗尽后的单次无工具 partial 收尾、元数据转发重送。
- 主要保障：隔离写入、严格验收后应用、并发漂移拒绝、截止/取消的进程收尾、未知提交状态保全、失败结构化交回。
- 不能承诺：错误都可自动修好、测试失败自动回写修复、任何写入自动 rollback、任意线程立即取消、应用崩溃自动接着做。

### 关键实际限制

1. 自动恢复最强的是 **已提交内容重放、元数据对账、幂等补投**；系统没有由这些存储机制提供的“崩溃后自动从原工具步骤继续跑”。
2. `memory.json.bak` 与 migration quarantine 保存诊断/迁移原件，代码没有遇到任意坏 JSON 就自动回滚到备份；Session base 和 Run metadata 全损坏也没有通用自动重建。
3. canonical success 与 projection failure 分开；这避免重复业务提交，但 UI 派生视图可能暂时过时。畸形 Session index 需要人工修复，不能把注释中的“rebuildable”理解为已有完整自动 rebuild 命令。
4. 有界 receipt、scan、lease、lock timeout 都会停；无可靠 ack 时推迟维护是恢复边界，不等于清空欠账。运行日志失败不会逆转真实工具执行。
5. D13 reload 失败时保留原异常；并非每种磁盘错误都能恢复进程内视图。权限、空间、根路径变化、authority corruption 通常要环境或用户解决。
